`botorch_rs.test_functions` re-exports the same problems as
`botorch.test_functions` (all but DH1–DH4, as in BoTorch). In Rust:
`botorch_core::test_functions::MultiObjectiveTestProblem::new(MultiObjectiveKind::Dtlz2,
Some(6), Some(3))?.with_negate(true)`, with matrix and row-major (`*_rows`)
methods.

**Coverage** (`scripts/api_coverage.py`): `test_functions` goes from 21 to
**57 of 84** names (68%) and all of `botorch` from 92 to **128 of 773**
(17%). The report lists no missing parameters, methods or properties for any
of the new classes. In "What is not ported yet", the test-functions item
becomes: "test functions other than the 20 synthetic and the 33
multi-objective ones (multi-fidelity and constrained single-objective

Paragraph for the section:

> The multi-objective test problems perform BoTorch's floating-point
> operations in BoTorch's order (e.g. torch evaluates `c / tensor` as
> `tensor.reciprocal() * c`), so that they agree to a few units in the last
> place. Penicillin needs a wider tolerance: its explicit Euler simulation is
> ill-conditioned, and perturbing the inputs by one unit in the last place
> changes BoTorch's own values by up to 6.6e-4 (relative, at 20000 random
> points). botorch-rust agrees with BoTorch to 1.6e-13 at those points (all
> of them stop at the same step), but ulp-level differences of `exp`, `expm1`
> and `pow` between math libraries could be amplified as much, so its values
> are compared relative to BoTorch's own sensitivity, like the Monte-Carlo
> quantities on nearly singular posteriors. Ten problems implement corrected
> definitions (BoTorch pull requests #3402 and #3405, see the migration
> notes): the tests compare them with replicas of the fixes, or with
> BoTorch's own classes when it contains them, and check that BoTorch main
> differs. Against the PR #3402 branch, the tests use BoTorch's own fixed
> classes for nine problems and confirm that the replicas reproduce them
> exactly; the fixtures generated from that branch are bitwise identical.

## Migration notes and known differences (items to add)

- **Multi-objective test problems.** `botorch_rs.test_functions` has
  BoTorch's multi-objective problems with BoTorch's signatures; the
  keyword-only `seed` seeds the noise of nested-list inputs (torch and NumPy
  inputs use the caller's generator, as for the synthetic functions) and
  `gen_pareto_front(n, *, seed=None)` the quasi-random fronts. Evaluations
  run in float64: float32 inputs give float32 results that are the rounded
  float64 values (BoTorch computes in float32). As in BoTorch, inputs are
  validated against the bounds in the problem's dtype (`dtype=torch.float32`
  rounds e.g. DH4's lower bound -0.15, so the problem accepts its own float32
  corners) and `ref_point` is fixed when the problem is created.
  `noise_std`, `constraint_noise_std` and `negate` can be reassigned (this
  reseeds the generator of list inputs). There is no autograd through the
  test problems. `problem.deviation` describes the corrected definitions.
- **Corrected definitions.** botorch-rust implements the fixes of two open
  BoTorch pull requests, so these problems differ from BoTorch main and the
  released 0.18.1:
  - meta-pytorch/botorch#3402:
    - `BraninCurrin`, `ConstrainedBraninCurrin`: `max_hv` is 59.4066 and
      609.4038; BoTorch's NSGA-II estimates (59.3601, 608.4004) are exceeded
      by evaluated points.
    - `DH4`: `max_hv` depends on `dim`, since `h < 0` for `x_0 > 0.98534`,
      where `f_1` decreases with `g`.
    - `DTLZ1`: `max_hv` subtracts the simplex volume `0.5^M / M!` (BoTorch:
      `1 / 2^M`, which is below attained hypervolumes).
    - `DTLZ4`: the position variables are mapped to `x_i^100`; BoTorch's
      DTLZ4 never uses its `alpha` and equals DTLZ2.
    - `ZDT3`: the second objective is multiplied by `g`, as in Zitzler et al.
      (2000).
    - `C2DTLZ2`: the constraint of Jain & Deb (2014) subtracts `r²` once
      (BoTorch subtracts it inside the sums, which enlarges the feasible
      regions), with `r = 0.4` for `M = 3` and `0.5` for `M > 3`; batched and
      one-dimensional inputs work (BoTorch raises `NotImplementedError` and
      `IndexError`); `max_hv` is the exact value for `M = 2` (0.3823336) and
      unknown for `M > 2`.
    - `SRN`: the first objective uses `(x_1 - 1)²` and the first constraint
      is `x_0² + x_1² <= 225`, as in Srinivas & Deb (1994).
    - `WeldedBeam`: the constraint slack is the negated pymoo constraint
      value; BoTorch's feasibility is inverted.
  - meta-pytorch/botorch#3405: `GMM` has float64 parameters; BoTorch creates
    them in float32, so it evaluates float64 inputs in float32 and returns
    float32 values (botorch-rust agrees with them to 2.5e-7). The same pull
    request gives each `ToyRobust` its own Levy function (no numerical
    effect on the CPU).
  - No pull request yet: `C2DTLZ2.gen_pareto_front` returns only feasible
    points. BoTorch inherits DTLZ2's front, the whole positive unit sphere,
    of which 57% of the points are feasible for `M = 2` (45% with the
    constraint of #3402).
- **Pareto fronts.** The ZDT fronts equal BoTorch's. The DTLZ fronts are
  quasi-random: BoTorch scrambles torch's `SobolEngine` with torch's global
  generator, botorch-rust uses its own scrambled Sobol sequence (seeded with
  `seed`), so the points differ but have the same distribution (more than
  `2^16` points come from several independently scrambled sequences).
  C2DTLZ2's feasible front is drawn from the same points by rejection.
- **Errors.** BoTorch's errors and messages for invalid sizes and noise
  lists. botorch-rust reports some invalid configurations when the problem is
  created, where BoTorch fails later: `num_objectives < 1` for the DTLZ
  problems, `DTLZ7` with one objective (BoTorch cannot evaluate it), and a
  `constraint_noise_std` list (or a non-list `noise_std` sequence) whose
  length does not match (BoTorch: a broadcasting error in `forward` /
  `evaluate_slack`). `penicillin_vectorized` validates the bounds.

## Notes for the maintainer

- BoTorch bugs found besides those of #3402 and #3405:
  - `C2DTLZ2.gen_pareto_front` returns infeasible points (implemented as a
    deviation):

    ```python
    import math, torch
    from botorch.test_functions.multi_objective import C2DTLZ2
    p = C2DTLZ2(dim=3, num_objectives=2)
    F = p.gen_pareto_front(100)
    x0 = torch.atan2(F[:, 1], F[:, 0]) * 2 / math.pi  # pre-image on the Pareto set
    X = torch.stack([x0, torch.full_like(x0, 0.5), torch.full_like(x0, 0.5)], dim=-1)
    print(torch.allclose(p.evaluate_true(X), F))          # True
    print(p.is_feasible(X, noise=False).double().mean())  # 0.57 (0.45 with #3402)
    ```
  - `DTLZ7(dim=3, num_objectives=1)` constructs, but `evaluate_true` raises
    `RuntimeError: stack expects a non-empty TensorList`.
  - Docstrings that contradict the code (botorch-rust follows the code):
    `MOMFPark` (code `+ x4 sin(x3) A - x3 + B`, docstring
    `- x4 sin(x3) A + x3 - B`) and `MOMFBraninCurrin` (Currin denominator
    `4 * x1` in the code, `4 * x_2` in the docstring).
- With one objective, BoTorch's DTLZ5 still applies `cos(x_0 pi / 2)` (its
  angles always start with `x_0`); botorch-rust does the same.
- Penicillin's sensitivity to rounding is a property of the benchmark
  (explicit Euler steps of one time unit), not a bug.
- `scripts/generate_fixtures.py` gains only the `5a-tf` choice and its hook;
  the pre-existing ruff findings in that file and in
  `scripts/benchmark_optimize_acqf.py` are unchanged. `CONTRIBUTING.md` lists
  the fixture phases (`--phase 1|2|4|4b|all`) and could mention `5a-tf`.
