## How it works

- **Element-wise kernels** (`botorch_core::utils::elementwise`): one Rust
  function per name evaluates BoTorch's expression operation by operation
  (with float32 constants and rounding points for float32 arrays) and its
  exact derivatives with respect to every input (dual numbers `Dual<6>` for
  the `bvn` family); reductions (`logsumexp`, `logmeanexp`, `smooth_amax`,
  `smooth_amin`, `fatmax`, `fatmin`) work on rows with BoTorch's
  `_inf_max_helper` treatment of infinities. `_ops.py` broadcasts, reshapes
  and permutes the reduced dimensions and wraps both in
  `torch.autograd.Function`s, so torch inputs keep autograd (first order).
  Gradients with respect to a scalar `tau` of the reductions use Euler's
  relation for these positively homogeneous functions,
  `dF/dtau = (F - sum_i x_i dF/dx_i) / tau`.
- **torch's CPU generator** (`utils::torch_rng::TorchGenerator`): mt19937
  seeded like `torch.manual_seed`, 53-bit doubles from `random64`, float32
  `rand` from 24 bits, `randn` as torch's `normal_fill` (blocks of 16 with a
  recomputed tail) for 16 or more values and the cached Box–Muller
  `normal_distribution` below. Bit-exact against torch for every tested seed
  and size; it gives `IIDNormalSampler` torch's draws without torch.
- **IID base samples in the MC acquisition functions**: Rust's
  `SobolQMCNormalSampler` got a `BaseSampleSource`; `SobolQMCNormalSampler::iid`
  fills `num_samples x dim` base samples with `torch.randn(num_samples, dim)`
  after `torch.manual_seed(seed)` in BoTorch's layout (`S x 1 x q x m`
  flattened), so every MC acquisition function, fantasy model and look-ahead
  takes either sampler without other changes. The Python side checks
  `isinstance(sampler, NormalMCSampler)` where it checked
  `SobolQMCNormalSampler`.
- **MVNXPB** keeps BoTorch's `mvnxpbState` (pivoted Cholesky factor, plug-in
  estimates, running log probabilities) in a Rust `MvnxpbState`, so that
  partial solves, pivots, `augment`, batching operations and conversions to
  and from BoTorch's dictionaries are exact; the log-probability gradient
  comes from phase 8's chunked dual-number solver.
- **LinearEllipticalSliceSampler**: the constraints are standardized in
  Rust; each step takes the direction and the uniform number from the
  caller's generator in BoTorch's order (torch: `randn_like(z)`, then
  `rand(num_chains)`), computes the intersection angles, the active arcs,
  BoTorch's trimming and the new point natively.
- **Test functions**: `SingleObjectiveProblem` evaluates all 19 problems in
  Rust (`evaluate_true`, `evaluate_slack_true`, `cost`); TrajectoryPlanning
  reproduces SciPy's FITPACK interpolating spline (`splprep(k=3, s=0)`,
  `splev`) and the obstacle penalties.
- **QMC engines**: multivariate projection (`base_samples @ root + mean`)
  runs in Rust with the GIL released, using float32 matrix arithmetic for
  float32 outputs. The torch-free Sobol engine keeps one native seed and a
  cursor, so successive draws continue the same sequence even when no seed
  is supplied. It rejects requests beyond its supported 65,536 points
  without advancing the cursor.
- **optimize_posterior_samples** draws BoTorch's scrambled Sobol candidates
  from torch's global generator and maximizes the restarts with SciPy's
  L-BFGS-B as one joint problem, like BoTorch's `gen_candidates_scipy`
  without the parallel mode (the restarts' leading dimensions pair them with
  the sample paths, so the paths are evaluated on all restarts at once).

## Deviations from BoTorch (migration notes)

1. `LinearEllipticalSliceSampler` wraps negative intersection angles with
   2 pi in float64; BoTorch's are 1.7e-7 too large (bug 1), so chains
   agree with BoTorch's only once BoTorch's `_twopi` is replaced by a
   float64 tensor (then to 2e-12 over 100 steps).
2. Python-float `best_f` / `tau` / `eta` stay float64 in botorch_rs;
   BoTorch rounds them to float32 buffers (`torch.as_tensor(best_f)`,
   `torch.full(..., eta)`), which changes qEI values by up to ~6e-9
   relative for `best_f = 0.4` and `compute_smoothed_feasibility_indicator`
   by 2e-9 for `eta = 0.1` (see `docs/clamp-subgradients.md`). The parity
   tests use float32-representable values.
3. `fatmax` / `fatmin` gradients with a `-inf` entry below a finite maximum
   are the limits (0 for that entry); BoTorch's are NaN for the whole row
   (bug 3).
4. `log_softplus` accepts tensor temperatures (element-wise, and with
   gradients); BoTorch raises `TypeError` (bug 2).
5. `MVNXPB.solve()` on an already solved odd-dimensional problem is a no-op;
   BoTorch raises `UnboundLocalError` (bug 4).
6. `TrajectoryPlanning.evaluate_true` accepts any `batch_shape x d`; BoTorch
   only `n x d` (bug 5).
7. `separate_mtmvn` returns the correct per-task blocks of batched
   interleaved multitask normals (BoTorch: wrong values, bug 6).
8. `HitAndRunPolytopeSampler` chains use botorch_rs's generator (phase 9,
   compared statistically in `test_parity_constraints.py`); the normalized
   constraint system and interior points (the same smallest slack; the
   linear program's maximizer need not be unique) match BoTorch.
9. `TruncatedMultivariateNormal`, `UnifiedSkewNormal`, `BufferDict` and
   `optimize_posterior_samples` need torch, the pymoo classes pymoo,
   `DelaunayPolytopeSampler` SciPy (as in BoTorch).
10. Without torch, `IIDNormalSampler` still produces torch's draws (native
    generator); `LinearEllipticalSliceSampler`, `HitAndRunPolytopeSampler`
    and `AckleyMixed(randomize_optimum=True)` draw from NumPy's global
    generator for NumPy inputs and from Python's `random` for lists.
11. `percentile_of_score` of torch tensors has torch's default dtype (as
    BoTorch); of NumPy arrays and lists float64.
12. `propagate_grads` has no effect: botorch_rs's gradients are exact.
13. `qLogNoisyExpectedImprovement` ignores `cache_root` (phase 8): with an
    `IIDNormalSampler` it equals BoTorch's `cache_root=False`.

## BoTorch bugs found

1. **`LinearEllipticalSliceSampler` wraps angles with 2 pi in float32.**
   `_find_intersection_angles` computes `theta + theta.lt(0.0) * _twopi`: a
   bool tensor times a Python float has torch's default dtype, so 2 pi is
   rounded to 6.2831854820251465 (1.7e-7 too large) and every wrapped arc
   end misses the constraint boundary; the trimmed arcs (1e-12) can then
   reach outside the polytope.

   ```python
   import torch
   from botorch.utils.probability.lin_ess import LinearEllipticalSliceSampler
   DT = torch.float64
   A = torch.tensor([[1.0, 1.0], [-1.0, 0.0]], dtype=DT)
   b = torch.tensor([[1.0], [0.5]], dtype=DT)
   s = LinearEllipticalSliceSampler(inequality_constraints=(A, b))
   nu = torch.tensor([[0.3], [-1.2]], dtype=DT)
   alpha, beta = s._find_intersection_angles(nu)
   p, q = s._Az @ s._z, s._Az @ nu
   print((p * alpha.cos() + q * alpha.sin() - s._bz).abs().max())  # 2.5e-07, not ~1e-16
   print((torch.tensor([True]) * (2.0 * 3.141592653589793)).dtype)  # torch.float32
   ```

   Fix: `theta1 + theta1.lt(0.0).to(theta1) * _twopi` (or
   `torch.where(theta1 < 0, theta1 + _twopi, theta1)`).

2. **`log_softplus` fails for a tensor `tau`.** It passes `beta=(1 / tau)`
   to `softplus`, which needs a number: a 0-dim tensor that requires
   gradients and any tensor with several elements raise `TypeError`
   (`softplus(): argument 'beta' must be Number, not Tensor`), although the
   signature accepts `tau: float | Tensor`.

   ```python
   import torch
   from botorch.utils.safe_math import log_softplus
   log_softplus(torch.randn(3, dtype=torch.float64), tau=torch.tensor([0.5, 1.0, 2.0]))  # TypeError
   ```

   Fix: `softplus(x / tau) * tau` with the threshold applied to `x / tau`.

3. **`fatmax` / `fatmin` gradients are NaN for a row with a `-inf` entry.**

   ```python
   import math, torch
   from botorch.utils.safe_math import fatmax
   x = torch.tensor([1.0, -math.inf, 0.5], dtype=torch.float64, requires_grad=True)
   fatmax(x, dim=-1).backward()
   print(x.grad)  # tensor([nan, nan, nan]); the limit is finite (0 for the -inf entry)
   ```

   The NaN of the `-inf` entry's derivative reaches every entry of the row
   through the shared normalization.

4. **`MVNXPB.solve()` twice raises `UnboundLocalError` for odd dimensions.**

   ```python
   import torch
   from botorch.utils.probability.mvnxpb import MVNXPB
   m = MVNXPB(torch.eye(3, dtype=torch.float64), torch.tensor([[-1.0, 1.0]] * 3, dtype=torch.float64))
   m.solve()
   m.solve()  # UnboundLocalError: cannot access local variable 'Phi_i'
   ```

   The factor of a final unpaired variable uses `Phi_i`, which is only
   assigned inside the main loop; that loop does not run once the solver is
   complete.

5. **`TrajectoryPlanning` only evaluates `n x d` inputs.** `_evaluate_true`
   iterates over the first dimension, so a `batch_shape x n x d` input
   fails:

   ```python
   import torch
   from botorch.test_functions.synthetic import TrajectoryPlanning
   TrajectoryPlanning(dim=4)(torch.rand(2, 3, 4, dtype=torch.float64))
   # RuntimeError: shape '[2, 2]' is invalid for input of size 12
   ```

   Fix: `X.reshape(-1, d)`, evaluate, reshape to `batch_shape`.

6. **`separate_mtmvn` returns wrong covariances for batched interleaved
   multitask normals** (linear_operator's `BlockDiagLinearOperator`
   slicing; reported as linear_operator PR #142 in the audit). The parity
   test compares with the diagonal blocks of the dense covariance.

7. **Python-float parameters become float32 buffers** (`best_f`, `tau` of
   the MC acquisition functions, `eta` of
   `compute_smoothed_feasibility_indicator` through `torch.full`):
   documented in `docs/clamp-subgradients.md`;
   `compute_smoothed_feasibility_indicator([lambda Y: Y[..., 0]], Y, eta=0.1)`
   at `Y = 0.3` gives `sigmoid(-0.3 / float32(0.1))`, 2e-9 off.

Known from earlier phases and still present: `bvn` gradients NaN at some
inputs and MVNXPB gradients of batches whose members pivot differently
(phase 8, reported upstream).

8. **`as_ndarray` raises `KeyError` with an explicit NumPy dtype and
   `inplace=False`.** The branch deciding whether to clone indexes
   `torch_to_numpy_dtype_dict` with a NumPy dtype, although the dictionary
   has torch dtypes as its keys. This is reproducible in released BoTorch
   0.18.1:

   ```python
   import numpy as np
   import torch
   from botorch.optim.utils.numpy_utils import as_ndarray
   as_ndarray(torch.ones(2), dtype=np.float32, inplace=False)  # KeyError
   ```

   Fix: compare `np.dtype(torch_to_numpy_dtype_dict[out.dtype])` with
   `np.dtype(dtype)`, or use NumPy's `astype(dtype, copy=...)` directly.
   The port uses the latter and verifies that `inplace=False` never aliases
   the original storage, for matching and differing dtypes.

## Verification

The optimization follow-up adds native equality projection (including first
derivatives of points, coefficients and right-hand sides), native SLSQP
projection with nonlinear constraints and per-row fixed features, and KG
value-function initialization using the existing Rust acquisition optimizer.
The value-function initializer preserves fantasy batch shapes. Its inner
optimizer inherits the port's Sobol stream; complete initializer outputs need
not be bit-for-bit identical to Torch's optimizer. Component parity is checked
with the same optimized solutions, alongside real native optimization tests.

**Deliberate upstream correction:** official BoTorch `b0dd01be6` and released
0.18.1 call `standardize(function_values)` inside `boltzmann_sample`, although
scores have shape `batch_shape x num_categories`. For more than one dimension,
`standardize` normalizes along `-2`, across a batch dimension. Repeated fantasy
score rows therefore become all-zero standardized scores and receive uniform
sampling probabilities. Higher-valued optimized solutions have no advantage.
The precise upstream fix is
`standardize(function_values.unsqueeze(-1)).squeeze(-1)`, which normalizes over
categories and leaves the one-dimensional case unchanged. The Rust port
applies that corrected category-axis behavior, including batched restart
selection and value-function initialization. Its parity tests patch only this
axis expression in the reference; frequency regressions require a high-value
solution to receive more than 80% of draws in every fantasy batch (the bug
would give approximately one third). Scalar/unbatched sampling and shared
temperature reduction on overflow are checked against the reference too.

Projection also rejects a native SLSQP "success" whose returned point violates
constraints or bounds. A conflicting bound/inequality regression covers this
case, so a failed projection cannot quietly return infeasible candidates.

The public cached-Cholesky sampler mixin now reuses the existing native root
decomposition and low-rank sampling routines. Normal samplers expose their
generated base samples and can extend ordinary Gaussian posteriors while
preserving baseline normals. Baseline roots broadcast over candidate batches.
Private base-sample updates for structured/Matheron posterior layouts are
explicitly unsupported; those models can still use their normal sampling
fallback, and their existing native acquisition implementations are unchanged.
The 54 sampler/mixin tests pass, along with 18 existing IID acquisition parity
tests (values and input gradients) against official `b0dd01be6`. IID base-sample
updates match the reference exactly; Sobol retains its documented native
scrambling stream.

The hierarchical parsing helpers match official forest partitions and paths.
They additionally reject cycles, duplicate children and out-of-range indices.
Official `get_index_to_path(2, {0: {0: [1]}, 1: {0: [0]}})` silently returns an
empty dictionary because its traversal starts only from orphan roots. The
port validates every component before traversal, including rootless cycles.
All 20 hierarchy tests pass, including a depth-1200 forest handled iteratively.

The initial committed branch passed all three phase 11a Python suites on
2026-10-20 against the local BoTorch fork checkout at `c98dd9452`
(`fix/audit-correctness-fixes`, not official upstream main), with
