# Preference learning

The port of BoTorch's preference learning (roadmap phase 10b): the supported
API, how it works, the deviations from BoTorch, the equivalence results and
the BoTorch bugs found.

`PairwiseGP` with its Laplace approximation, likelihoods and marginal log
likelihood, the preference acquisition functions (analytic EUBO, qEUBO,
pairwise BALD, `PairwiseMCPosteriorVariance`), `LearnedObjective`, and the
pairwise and IID samplers, and the input constructors of EUBO and qEUBO.
Reference: BoTorch main at da00e0401 and BoTorch 0.18.1 (identical in all
files of this phase), torch 2.13 and 2.14.1, scipy 1.18.

The current [PairwiseGP input-transform audit](pairwise-input-transforms.md)
supersedes the original phase's learned-transform restriction. Native Warp
fitting, full Laplace gradients, shared/per-member batch ownership, nested
conditioning, and atomic data replacement are validated against official
BoTorch revision `b0dd01be6`.

The branch is merged with main at 41b2ae3 (phase 8b): the EUBO constructors
are registered in phase 8b's input-constructor registry,
`LearnedObjective`'s vector-Jacobian product uses phase 8b's
`posterior_samples_with_vjp`, and `qMultiStepLookahead` rejects a
`PairwiseGP` with BoTorch's error. Phase 8b has no `IIDNormalSampler`; the
one of this phase is the only one.

Rust: `botorch_core/src/minpack.rs` (new), `models/pairwise_gp.rs` (new),
`models/likelihoods/{mod,pairwise}.rs` (new), `acquisition/preference.rs`
(new). Bindings: `botorch_pyo3/src/preference.rs` (new). Python:
`botorch_rs/models/pairwise_gp.py`, `models/likelihoods/`,
`acquisition/preference.py`, `acquisition/active_learning.py`
(`PairwiseMCPosteriorVariance`), `acquisition/objective.py`
(`LearnedObjective`), `sampling/pairwise_samplers.py`, `sampling/normal.py`
(`IIDNormalSampler`), `acquisition/input_constructors.py` (the EUBO
constructors). Tests: `botorch_core/tests/preference_10b_parity.rs`
(fixtures in `botorch_core/tests/fixtures/10b_preference/`, generated by
`scripts/generate_fixtures.py --phase 10b-preference` from

## How it works

- **Laplace approximation** (BoTorch's `_update`): the training covariance
  `K` with `_ensure_psd_with_jitter` (jitter 0, `j`, `10 j` on `K / s`,
  `s` the outputscale) and its `psd_safe_cholesky` factor (jitter `j ..
  1e5 j`, BoTorch's 6 tries); the MAP utility from MINPACK's `hybrj`
  (scipy's `fsolve` with the Jacobian `H(f) + (L Lᵀ)⁻¹`, `xtol = 1e-6`,
  `maxfev = 100` by default), warm-started from the previous solution or,
  for new data, from the standardized win counts plus `0.05` times numpy's
  `np.random.standard_normal` draws (BoTorch's global generator, so that
  `np.random.seed` gives BoTorch's starting points); then BoTorch's two
  Newton steps. Unbatched data are consolidated (`consolidate_duplicates`).
- **MINPACK `hybrj`** is ported line by line (`hybrj`, `dogleg`, `qrfac`
  without pivoting, `qform`, `r1updt`, `r1mpyq`, `enorm`); no nonlinear
  solver crate is available offline. On systems whose values Rust and Python
  compute bitwise identically (Rosenbrock, Powell singular, Broyden
  tridiagonal and banded, a system without a root, a `maxfev` limit) every
  evaluation point, the solution, `info`, `nfev` and `njev` are scipy 1.18's
  bitwise, through Jacobian re-evaluations, rank-one updates and the
  terminations `info = 1, 2, 4, 5`.
- **The MLL gradient** is BoTorch's autograd gradient: the derivative
  through the two Newton steps with the fsolve solution held fixed (at the
  solution this is the implicit-function derivative of the Laplace
  evidence; the second step removes the first step's error to second
  order), computed in reverse mode: the adjoints of the Newton systems
  `(K H + I)⁻¹ K g`, of the likelihood's Hessian (third derivatives of the
  probit and logit log likelihoods), of `(L Lᵀ)⁻¹` and of `log det(K H(f₁) +
  I)`, contracted with the kernel's derivatives (any kernel tree).
- **The posterior** is BoTorch's eval-mode `forward`, with the Cholesky
  factor of the covariance (jitter as BoTorch's) as the reported covariance
  `L Lᵀ`; input gradients are exact (forward mode, through input
  transforms). `PairwiseGP` implements the `Model` trait, so all acquisition
  functions of botorch_rs work on it.
- **Fits**: `fit_gpytorch_mll` runs L-BFGS-B (botorch_rs's port of scipy's)
  on the raw hyperparameters; every evaluation recomputes the Laplace
  approximation warm-started from the previous evaluation, as BoTorch's
  closure does, and the model keeps the state of the last evaluation at the
  optimum.

## What remains unported (in this area)

- Learned Warp transforms are implemented natively, including their full
  Laplace-evidence derivatives; see the current audit linked above for
  supported chains and parameter batch shapes. One-to-many transforms
  (`InputPerturbation`), reverse warping, and coefficient-learning steps
  after a learned transform retain explicit errors.
- The initial learned-objective MC gap is resolved; see the current audit
  linked above. Stochastic learned objectives use full-joint noisy improvement
  sampling to preserve preference correlations, correcting the official
  cached-root path. Pointwise deterministic preferences retain cached roots.
- `IIDNormalSampler` in the Monte-Carlo acquisition functions (they use
  `SobolQMCNormalSampler`'s fixed base samples); the rest of phase 11's
  samplers.
- Batched data whose kernels have a batch shape other than `()` (shared
  parameters) or the data's batch shape (parameters per batch element), e.g.
  a broadcast batch shape: `UnsupportedError`.
- `fit_gpytorch_mll_torch` on a `PairwiseGP`, torch autograd through the
  likelihood functions and through `mll(...)` (use `value_and_grad`),
  `RankingDataset` / `SliceContainer` (BoTorch's are accepted by
  `construct_inputs`).
- Preference test functions: BoTorch has none in `botorch.test_functions`.

## Deviations from BoTorch (migration notes)

1. **Pairwise samplers list the preferred item first** (BoTorch bug 1):
   fantasies condition on the sampled preferences, not their reverse.
2. **A comparison of two near-duplicate datapoints is uninformative**
   (BoTorch bug 2): after consolidation it compares an item with itself; its
   row of `D` is zero (probability 1/2, a constant `log 1/2` in the MLL).
3. **The logit likelihood's gradient is finite for utilities above ~709**
   (BoTorch bug 3); elsewhere it is BoTorch's expression.
4. **`LearnedObjective` with a multi-dimensional `sample_shape`** returns the
   documented `(sample_size * num_samples) x batch_shape x q` (BoTorch bug
   4); the values are in the same order.
5. **`num_outputs` of a prior-only `PairwiseGP` is 1** (BoTorch bug 5 raises
   `AttributeError`). `AnalyticExpectedUtilityOfBestOption` of a prior-only
   model raises BoTorch's `AttributeError`, as BoTorch reads
   `pref_model.datapoints` there.
6. Random numbers: the initial utility's perturbation comes from numpy's
   global generator (Python's `random` without numpy); BALD draws from the
   input's library (torch: BoTorch's draws, `torch.empty(shape).normal_()`),
   within `optimize_acqf` from botorch_rs's own generator; `IIDNormalSampler`
   draws torch's values for `seed` (numpy's `RandomState(seed)` or Python's
   `random.Random(seed)` without torch).
7. qEUBO with an `outcome_model` and an objective that depends on `X`:
   botorch_rs passes the candidates `X`, BoTorch the outcomes `Y`. Ties of
   the maximum over the `q` points share the gradient (BoTorch's `max`
   gives it to the first index); only exact ties differ.
8. A 1-dimensional `previous_winner` is accepted (BoTorch raises a shape
   error).
9. Errors: invalid comparison indices raise `BotorchRuntimeError` (a
   `RuntimeError`, with torch's message); the other exceptions are
   BoTorch's (`UnsupportedError`, `RuntimeError`, `AssertionError`,
   `ValueError`, `IndexError`, `AttributeError`, with the same messages).
10. `mll(...)` returns the value without an autograd graph; the MLL's
    gradient is `mll.value_and_grad()`.
11. **The t-batches of one call are independent** (BoTorch bug 6): the
    jitter of the prior covariance of the new points is decided per t-batch.
12. `qMultiStepLookahead` on a `PairwiseGP` (or a `ModelListGP` with one)
    raises BoTorch's `RuntimeError: Conditioning on non-pairwise comparison
    observations.` at construction; BoTorch raises it at the first
    evaluation, when it fantasizes.

## Equivalence tests

Tolerances: values 1e-9 (relative), gradients 1e-8 (relative to the largest
component). Where rounding decides a discrete step of BoTorch's algorithm,
the comparison gives both libraries the same input instead of a wider
tolerance. Rounding differs between libraries and between platforms (in
botorch_rs through the platform's libm, in torch through its BLAS / LAPACK):
on seed 16 of the sweep, botorch_rs's values differ by up to 1.4e-15 between
Windows and Linux, BoTorch's by up to 1.3e-15, and BoTorch's fsolve takes 3
Jacobian evaluations on Windows and 2 on Linux.

- **The fsolve solution** `_x0` is not compared. fsolve stops after a step
  of relative size `xtol`, and where `cond(K)` reaches 1e10 .. 1e15
  rounding moves its iterates within that (the solutions differ by up to
  3.1 `xtol` in the sweep). Instead BoTorch's two Newton steps from
  botorch_rs's fsolve solution must give botorch_rs's utility to 1e-9 (in
  the Rust fixtures, botorch_rs's Newton steps from BoTorch's solution,
  `PairwiseGP::laplace_from_solution`, BoTorch's utility); the utilities
  themselves are compared to 1e-9 as well.
- **`covar_chol` and `covar_inv`** are compared normwise to
  `max(cond(K) · eps, 1e-9)`, the accuracy of a Cholesky factor and of an
  inverse of `K` (Higham, *Accuracy and Stability of Numerical Algorithms*,
  Thm. 10.8 and Sec. 14.1).
- **Jitter decisions.** BoTorch adds jitter to the prior covariance of the
  new points (`_ensure_psd_with_jitter`) and to posterior covariances
  (`psd_safe_cholesky`) where a Cholesky factorization fails. For a matrix
  whose smallest eigenvalue is within `20 n^{3/2} u ||A||` of zero
  (Demmel's bound, Higham Thm. 10.7) the outcome depends on rounding: with
  a linear kernel on one input (sweep seed 16) every pair's prior
  covariance is rank one, and torch's factorization fails for t-batches 0
  and 2 on Windows but for 1 and 2 on Linux. Every t-batch is evaluated on
  its own (BoTorch couples the t-batches of one call, bug 6). A t-batch
  that differs must contain such an ambiguous decision and must match, at
  1e-9 / 1e-8, BoTorch's result for the other outcome
  (`preference_helpers.BtJitterDecisions` replays BoTorch's decisions with
  the ambiguous ones flipped).
  The test oracle's alternate successful factor uses a representable
  `eps * ||A||` positive margin when `2 * abs(lambda_min)` is zero or too
  small to change the diagonal. Retries remain inside that same Demmel
  budget. Exact-zero and nonfinite matrices are not ambiguous; genuinely
  indefinite matrices still fail. This repairs a test-helper Cholesky
  failure observed in the post-release Linux Torch 2.14.1 CPU run, without
  changing either implementation or the comparison tolerances.
- **Sample-based quantities** (qEUBO, BALD) of a t-batch whose factorized
  posterior covariance is singular within rounding: the Cholesky factor of
  a singular matrix is Hoelder continuous with exponent 1/2, so a
  perturbation within the ambiguity bound changes it by up to
  `sqrt(20 n^{3/2} u) = 7.9e-8` (relative); that is their tolerance.

Twins are used for fits only (the two-stage procedure of
`docs/fitting.md`). Earlier versions of the sweep compared
rounding-dependent quantities with BoTorch's spread on 16 twins; on Linux
all twins of seed 16 made the same jitter decisions, so the spread
(1.5e-11) missed the difference of the coupled, flipped decision (EUBO
1.0e-6), which failed CI.

### Randomized sweep (`test_equivalence_10b_preference.py`, `-m equivalence`)

dimensions (scale 1 or 3), 2 .. 3n random comparisons (with two
near-duplicate datapoints in some cases; comparisons of a near-duplicate
with its original are left out, see BoTorch bug 2), probit or logit,

(10 fits, on twins). Seed 16 (a linear kernel on one input) has ambiguous
jitter decisions in its EUBO / qEUBO / BALD t-batches, seed 39 in its joint
posterior.

## BoTorch bugs found

1. **The pairwise samplers list the item with the smaller sampled utility
   first.** `PairwiseMCSampler.forward` builds `c1 = np.choose(prefs,
   pairs.T)` with `prefs = s[i1] > s[i2]`, which picks the second item of a
   pair when the first is preferred; `PairwiseGP` reads `[i, j]` as "`i` is
   preferred over `j`", so fantasies (e.g. in the knowledge gradient)
   condition on reversed preferences:

   ```python
   model = PairwiseGP(torch.rand(6, 2, dtype=torch.float64), torch.tensor([[0, 1], [2, 3]]))
   post = model.posterior(torch.rand(3, 2, dtype=torch.float64))
   comps = PairwiseSobolQMCNormalSampler(torch.Size([2]), seed=5)(post)
   y = SobolQMCNormalSampler(torch.Size([2]), seed=5)(post).squeeze(-1)  # the same samples
   [bool(y[k, w] > y[k, l]) for k in range(2) for w, l in comps[k].tolist()]  # all False
   ```

   Fix: `c1 = np.choose(1 - prefs, cpt)`, `c2 = np.choose(prefs, cpt)`.
2. **A comparison of two near-duplicate datapoints becomes a wrong
   likelihood term (probit) or a crash (logit).** Consolidation maps the
   two items to one index; `D` is filled by two `scatter_` calls, so the row
   keeps `-1` at the item: the probit term is `Φ(-f_i/√2)` (it pushes the
   item's utility down; the true term is the constant 1/2), and the logit
   likelihood's `negative_log_gradient_sum` pairs winners and losers from
   `(D == 1).nonzero()` and `(D == -1).nonzero()`, which now differ in
   length: a shape error, or (with two comparisons, where the lengths
   broadcast) a silently wrong gradient:

   ```python
   X = torch.tensor([[0.1, 0.2], [0.5, 0.9], [0.10001, 0.2], [0.7, 0.4]], dtype=torch.float64)
   comps = torch.tensor([[0, 1], [2, 0], [3, 1]])    # 2 duplicates 0 within atol=1e-4
   PairwiseGP(X, comps).D                             # second row: [-1, 0, 0]
   PairwiseGP(X, comps, likelihood=PairwiseLogitLikelihood())
   # RuntimeError: The size of tensor a (2) must match the size of tensor b (3) ...
   ```

   Fix: drop such comparisons after consolidation (or build `D` with
   `index_add_` so that the row is `e_i - e_i = 0`).
3. **The logit likelihood's gradient overflows** to NaN when both
   utilities of a comparison exceed ~709 (`ey / (ex + ey)` with `ex = ey =
   inf`):
   `PairwiseLogitLikelihood().negative_log_gradient_sum(torch.tensor([800.,
   800.], dtype=torch.float64), torch.tensor([[1., -1.]], dtype=torch.float64))`
   is `[nan, nan]` (`[-0.5, 0.5]` at `[1, 1]`). Fix: `torch.sigmoid(u_l -
   u_w)`.
4. **`LearnedObjective` with a multi-dimensional `sample_shape` returns the
   wrong shape**: `samples.reshape(-1, *samples.shape[2:])` merges only the
   first sample dimension:
   `LearnedObjective(model, sample_shape=torch.Size([2, 3]))(torch.rand(4, 5, 1, 2,
   dtype=torch.float64)).shape` is `(6, 4, 5, 1)`, documented
   `(24, 5, 1)`. Fix: `samples.reshape(-1, *samples.shape[len(sample_shape) + 1:])`.
5. **A prior-only `PairwiseGP` has no `num_outputs`**:
   `PairwiseGP(None, None).num_outputs` raises `AttributeError`
   (`_num_outputs` is set in `set_train_data` only), so e.g.
   `PosteriorMean(PairwiseGP(None, None))(X)` and
   `ModelListGP(PairwiseGP(None, None)).num_outputs` fail although the
   model's posterior works. Fix: set `self._num_outputs = 1` in `__init__`.
   (`AnalyticExpectedUtilityOfBestOption` would still fail on such a model:
   it reads `pref_model.datapoints.dtype`.)

6. **The t-batches of one call are coupled through the jitter of the prior
   covariance.** `_ensure_psd_with_jitter` adds jitter to all t-batches
   when the factorization of any of them fails (`(info == 0).all()`), so a
   t-batch's posterior, and with it EUBO, qEUBO and BALD, depends on the
   other t-batches; a pair of identical points (a singular prior
   covariance) changes the value of another pair:

   ```python
   torch.manual_seed(0)
   model = PairwiseGP(torch.rand(6, 2, dtype=torch.float64), torch.tensor([[0, 1], [2, 3], [4, 5]])).eval()
   x = torch.rand(1, 2, 2, dtype=torch.float64)
   dup = torch.rand(1, 1, 2, dtype=torch.float64).expand(1, 2, 2)
   eubo = AnalyticExpectedUtilityOfBestOption(model)
   eubo(x).item(), eubo(torch.cat([x, dup]))[0].item()
   # 0.08521134858657567 vs 0.08521232834873171
   ```

   Fix: add the jitter per batch element (`info > 0`), as linear_operator's
   `psd_safe_cholesky` does.
